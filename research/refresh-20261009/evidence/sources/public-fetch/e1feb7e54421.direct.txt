In high-stakes domains, closing this gap requires supplying the model with the organization's own knowledge and priorities so its analysis reflects how the organization actually reasons.\u003c/p\u003e\n\n\u003cp\u003eThe system we have designed has four layers, each solving a distinct problem:\u003c/p\u003e\n\n\u003ctable\u003e\n  \u003cthead\u003e\n    \u003ctr\u003e\u003cth\u003eLayer\u003c/th\u003e\u003cth\u003eProblem It Solves\u003c/th\u003e\u003cth\u003eKey Insight\u003c/th\u003e\u003c/tr\u003e\n  \u003c/thead\u003e\n  \u003ctbody\u003e\n    \u003ctr\u003e\n      \u003ctd\u003eKnowledge System\u003c/td\u003e\n      \u003ctd\u003eInstitutional knowledge is scattered and inaccessible to AI.\u003c/td\u003e\n      \u003ctd\u003eLLMs are better at managing knowledge than people. Structure knowledge as a navigable filesystem, optimized for LLM consumption.\u003c/td\u003e\n    \u003c/tr\u003e\n    \u003ctr\u003e\n      \u003ctd\u003eReasoning Pipeline\u003c/td\u003e\n      \u003ctd\u003eExpert analysis follows structured methodologies that monolithic prompts cannot capture.\u003c/td\u003e\n      \u003ctd\u003eSeparate what the agent knows from how it reasons, using composable procedures we call recipes. This enables progressive disclosure, where the agent doesn't have to remember all the instructions at once.\u003c/td\u003e\n    \u003c/tr\u003e\n    \u003ctr\u003e\n      \u003ctd\u003eEvaluation Framework\u003c/td\u003e\n      \u003ctd\u003eYou cannot improve what you cannot measure.\u003c/td\u003e\n      \u003ctd\u003eDevelop automated benchmarks that grow with each improvement cycle to enable confident iteration.\u003c/td\u003e\n    \u003c/tr\u003e\n    \u003ctr\u003e\n      \u003ctd\u003eSelf-Improvement Loop\u003c/td\u003e\n      \u003ctd\u003eManual feedback cycles take weeks and do not scale.\u003c/td\u003e\n      \u003ctd\u003eTreat knowledge maintenance as a compilation problem with automated verification.\u003c/td\u003e\n    \u003c/tr\u003e\n  \u003c/tbody\u003e\n\u003c/table\u003e\n\n\u003cp\u003eThese layers depend on each other. The knowledge system's file structure makes automated editing possible. The reasoning layer's explicit procedures make failure attribution tractable. The evaluation framework gates every change. And the improvement loop feeds back into both knowledge and reasoning. Remove any one layer and the others degrade.\u003c/p\u003e\n\n\u003ch2\u003eBuilding the Organizational Second Brain\u003c/h2\u003e\n\n\u003cp\u003eLarge organizations can accumulate thousands of documents as a byproduct of expert work. It is tempting to treat those documents as organizational knowledge, but the real knowledge is implicit: how experts reason, what they prioritize, and how they resolve ambiguity. An agent that retrieves document chunks at inference time has to re-derive that reasoning from raw sources on every run, which is slow, error-prone, and inconsistent.\u003c/p\u003e\n\n\u003cp\u003eWe make that implicit knowledge explicit ahead of time. A long-running offline process reasons through source documents and distills them into structured knowledge files - curated statements of how the organization interprets its domain, with constraints, boundaries, and routing implications made machine-readable.\u003c/p\u003e\n\n\u003cp\u003eMost significantly, that knowledge then forms the basis of a feedback loop that allows the agent to learn from and implement feedback from human experts without the underlying model having to be retrained.\u003c/p\u003e\n\n\u003cp\u003eThe industry has converged on a similar idea. Andrej Karpathy's \u003ca href=\"https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f\" target=\"_blank\" rel=\"noopener\"\u003eLLM Wiki\u003c/a\u003e structures agent knowledge as a navigable graph of files, and Google's \u003ca href=\"https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing\" target=\"_blank\" rel=\"noopener\"\u003eOpen Knowledge Format\u003c/a\u003e standardizes this for cross-agent interoperability. The shared insight is that knowledge should be pre-extracted, explicitly structured, and progressively disclosed rather than re-derived on every query. We extended these principles into a system where citation fidelity and institutional consistency are non-negotiable, organizing 200+ files into a strict taxonomy:\u003c/p\u003e\n\n\u003cul\u003e\n  \u003cli\u003e\u003cstrong\u003ePosition files\u003c/strong\u003e capture authoritative organizational stances: how the organization has decided to interpret a given domain question, along with its constraints, boundary conditions, and machine-actionable routing implications that tell the reasoning layer when to apply it.\u003c/li\u003e\n  \u003cli\u003e\u003cstrong\u003eTaxonomy and vocabulary files\u003c/strong\u003e act as an authoritative glossary for the terms the organization uses to describe its domain, such as entity types, activity categories, and classification tiers. Each is maintained as a single source of truth so the agent and the organization use language consistently.\u003c/li\u003e\n  \u003cli\u003e\u003cstrong\u003eRouting indexes\u003c/strong\u003e map input characteristics to the relevant positions and procedures, determining which files apply without relying on embedding similarity alone. This makes retrieval deterministic and auditable.\u003c/li\u003e\n  \u003cli\u003e\u003cstrong\u003eGateway files\u003c/strong\u003e define threshold tests the agent must pass before entering an analytical domain, preventing it from applying specialized knowledge where it does not belong.\u003c/li\u003e\n\u003c/ul\u003e\n\n\u003cp\u003eEvery file declares its dependencies (\u003ccode\u003edepends_on\u003c/code\u003e) and consumers (\u003ccode\u003ereferenced_by\u003c/code\u003e) in YAML frontmatter, forming a bidirectional dependency graph. When one file changes, you can trace exactly what else might be affected, which matters when the self-improvement loop proposes automated edits.\u003c/p\u003e\n\n\u003cfigure\u003e\n  \u003cimg src=\"/static/img/blog/meta-organizational-second-brain/knowledge-system.body.webp\" data-full-src=\"/static/img/blog/meta-organizational-second-brain/knowledge-system.png\" alt=\"The knowledge system: files organized as a navigable filesystem, with YAML frontmatter declaring triggering scenarios, dependencies and consumers\" width=\"1280\" height=\"751\" loading=\"eager\" decoding=\"async\" fetchpriority=\"high\"\u003e\n  \u003cfigcaption\u003eAn illustration of the knowledge system: files are organized as a navigable filesystem (left), and each file's YAML frontmatter (right) declares when it applies (the triggering scenarios) plus its dependencies and consumers, forming a bidirectional dependency graph the agent can traverse and maintain easily.\u003c/figcaption\u003e\n\u003c/figure\u003e\n\n\u003ch2\u003eOrganizing Knowledge by Density and Usage Frequency\u003c/h2\u003e\n\n\u003cp\u003eA key architectural decision is how to partition knowledge between the curated wiki and supplementary retrieval (RAG). We split on \u003cstrong\u003einformation density and expected usage frequency\u003c/strong\u003e.\u003c/p\u003e\n\n\u003cp\u003e\u003cstrong\u003eHigh-density, frequently referenced sources go into the wiki\u003c/strong\u003e: distilled files capturing how the organization reasons, such as positions, decision frameworks, boundary examples, and strategic interpretations. The agent consults these on nearly every turn. Because they encode the organization's evolving thinking, they need to stay current, and the wiki structure makes them easy to update, version, and validate.\u003c/p\u003e\n\n\u003cp\u003e\u003cstrong\u003eSparse, situationally relevant sources are served through semantic or lexical search (RAG)\u003c/strong\u003e: documents that matter deeply when they apply but are not needed in detail on most runs, such as detailed reference material, individual product specifications, historical decision records, and niche external knowledge. Loading all of them into the wiki would bloat the system and dilute attention.\u003c/p\u003e\n\n\u003cp\u003eThe result is that the agent's core reasoning is always grounded in the most refined, current organizational knowledge, while it can still reach for supporting evidence when a scenario demands it. The combination produces an organizational second brain that encodes \u003cem\u003ehow\u003c/em\u003e the organization interprets and applies information, rather than only where to find it.\u003c/p\u003e\n\n\u003ch2\u003eExpert Reasoning via Composable Recipes\u003c/h2\u003e\n\n\u003cp\u003eKnowledge alone is not enough. Domain experts do not simply recall facts, they follow structured methodologies: a financial analyst works through a valuation model step by step, a security engineer follows a threat modeling procedure. The challenge is capturing those methodologies in a form an LLM can execute reliably.\u003c/p\u003e\n\n\u003cp\u003eWe solve this with \u003cstrong\u003ecomposable procedures we call recipes\u003c/strong\u003e. Where knowledge files are declarative, recipes are imperative. Each one prescribes a multi-step analytical workflow, specifying what to examine first, which knowledge to load at each step, what decision procedures to follow, and what constitutes a complete analysis.\u003c/p\u003e\n\n\u003cp\u003eThe critical design choice is \u003cstrong\u003eseparating what the agent knows from how it reasons\u003c/strong\u003e. Recipes reference knowledge files but contain no domain facts; knowledge files state positions but prescribe no procedures. This means:\u003c/p\u003e\n\n\u003cul\u003e\n  \u003cli\u003eAdding an organizational position means adding a knowledge file and updating a routing index. No recipe changes.\u003c/li\u003e\n  \u003cli\u003eFixing a flaw in the agent's methodology means editing a recipe. No knowledge files change.\u003c/li\u003e\n  \u003cli\u003eFailures attribute cleanly to one layer. Was the knowledge wrong, or the procedure?\u003c/li\u003e\n\u003c/ul\u003e\n\n\u003cp\u003eRecipes compose into pipelines, much like a head chef's master recipe for a dinner service delegates to sub-recipes for each component (the sauce, the protein, the garnish) without containing those details itself. Our top-level routing recipe examines the input and selects which downstream recipes to invoke, each handling one analytical phase.\u003c/p\u003e\n\n\u003cp\u003eThis is also what enables \u003cstrong\u003eprogressive disclosure\u003c/strong\u003e. Rather than front-loading a monolithic instruction set covering every possible scenario, each recipe step carries only the instructions and knowledge relevant to that phase. Early versions used a single flat instruction file and loaded all sources via semantic search, pulling a large volume of mixed-relevance files into the context window on every run. After restructuring into recipe-driven stages, each query touches only a small, targeted subset, cutting tokens consumed per turn by around 80%. Context windows are finite and attention degrades with volume, so delivering the right instructions at the right time directly improves reasoning quality.\u003c/p\u003e\n\n\u003ch2\u003eKeeping Humans in Control\u003c/h2\u003e\n\n\u003cp\u003eHuman experts stay in control of this system throughout. The agent accelerates and structures their work; it does not replace their judgment or their authority over the outcome.\u003c/p\u003e\n\n\u003cp\u003eWe enforce this through two mechanisms:\u003c/p\u003e\n\n\u003cul\u003e\n  \u003cli\u003e\u003cstrong\u003eCheckpoints\u003c/strong\u003e are defined points in the analysis where the agent surfaces its intermediate reasoning for expert review before proceeding, and the expert can confirm, correct, or redirect.\u003c/li\u003e\n  \u003cli\u003e\u003cstrong\u003eEscalations\u003c/strong\u003e trigger when the agent hits genuine ambiguity, whether from underspecified inputs or evidence that supports more than one defensible reading. Rather than forcing a resolution, it hands the question to the expert, whose choice determines the path the analysis takes.\u003c/li\u003e\n\u003c/ul\u003e\n\n\u003cp\u003eCheckpoints and escalations serve three purposes simultaneously:\u003c/p\u003e\n\n\u003cul\u003e\n  \u003cli\u003e\u003cstrong\u003eQuality and direction control\u003c/strong\u003e: experts catch errors before they compound downstream, and keep the analysis on the path they consider most relevant.\u003c/li\u003e\n  \u003cli\u003e\u003cstrong\u003eTraining signal\u003c/strong\u003e: every correction and every escalation becomes input for the self-improvement loop.\u003c/li\u003e\n  \u003cli\u003e\u003cstrong\u003eTrust calibration\u003c/strong\u003e: experts build confidence incrementally by observing the agent's reasoning rather than just its final output, and by seeing it flag uncertainty instead of masking it.\u003c/li\u003e\n\u003c/ul\u003e\n\n\u003cp\u003eThe more consequential the decision, the more this matters, which is why we recommend keeping a human in the loop by default across domains like compliance, financial risk assessment, security review, and engineering safety.\u003c/p\u003e\n\n\u003ch2\u003eThe Self-Improvement Flywheel\u003c/h2\u003e\n\n\u003cp\u003eWe consider the self-improvement flywheel to be the most distinctive part of this system. While the structured knowledge system and composable recipes produce a system that is legible by humans and agents, testable, and modular, the number of interdependent files makes manual maintenance impossible to scale. When domain experts provide feedback to an agent that feedback has to be translated into precise file edits. This process can take weeks because it requires understanding the full dependency graph, verifying nothing else breaks, and validating the fix actually works.\u003c/p\u003e\n\n\u003cp\u003eThere has been a large body of work - from RAG memory systems to model-weight knowledge editing - devoted to addressing how agents store, retrieve, and update knowledge. But much less attention has gone toward \u003cstrong\u003ekeeping a document-based institutional knowledge base correct\u003c/strong\u003e as it grows and as expert positions evolve. Agents that auto-draft their own fixes are increasingly common; but we have not seen this level of validation rigor applied to a structured knowledge base without model retraining.\u003c/p\u003e\n\n\u003cp\u003eWe treat that maintenance as a \u003cstrong\u003ecompilation problem\u003c/strong\u003e and automate it. Every expert correction moves through four phases:\u003c/p\u003e\n\n\u003col\u003e\n  \u003cli\u003eDiagnose expert feedback into actionable issues with their root cause.\u003c/li\u003e\n  \u003cli\u003eCompile issues into minimal verified edits.\u003c/li\u003e\n  \u003cli\u003eValidate that fixes work without regressions.\u003c/li\u003e\n  \u003cli\u003eHave domain experts review them.\u003c/li\u003e\n\u003c/ol\u003e\n\n\u003cp\u003eOnce the loop completes, the regression test suite is enriched with the issue that was just fixed so that future updates preserve this behavior.\u003c/p\u003e\n\n\u003cfigure\u003e\n  \u003cimg src=\"/static/img/blog/meta-organizational-second-brain/self-improvement-loop.body.webp\" data-full-src=\"/static/img/blog/meta-organizational-second-brain/self-improvement-loop.png\" alt=\"The self-improvement loop: diagnose, compile, evaluate, review and land, then fold the fix back into the regression suite\" width=\"1280\" height=\"714\" loading=\"lazy\" decoding=\"async\"\u003e\n  \u003cfigcaption\u003eThe self-improvement loop. Expert corrections are diagnosed to their root cause, compiled into minimal verified edits, and evaluated against replay and regression tests before they are reviewed and landed. Each fix is then folded back into the regression suite, so the gain is permanent.\u003c/figcaption\u003e\n\u003c/figure\u003e\n\n\u003ch3\u003eDiagnosis: Attributing Each Correction to a Root Cause\u003c/h3\u003e\n\n\u003cp\u003eRaw expert feedback comes from conversation traces where domain SMEs interacted with the agent and provided corrections. The diagnosis phase extracts structured signals from these conversations.\u003c/p\u003e\n\n\u003cp\u003eOur first approach classified feedback by conversational form. If the expert provided information, it must be a knowledge gap; if they redirected the agent, it must be a procedure problem. This heuristic failed because conversational form is a poor proxy for root cause. An expert correcting a conclusion might be exposing a knowledge gap, a recipe flaw, or a genuine ambiguity.\u003c/p\u003e\n\n\u003cp\u003eThe working approach separates extraction from classification. First, extract every substantive signal from the expert alongside the agent's full knowledge manifest (every file loaded, when, and how used). Second, read the actual knowledge files and apply a single attribution test: \u003cem\u003ecould the agent have reached the correct conclusion from its source materials?\u003c/em\u003e\u003c/p\u003e\n\n\u003cul\u003e\n  \u003cli\u003eIf the materials contained the right answer but the agent still erred: recipe problem.\u003c/li\u003e\n  \u003cli\u003eIf the materials did not contain the right answer: knowledge gap.\u003c/li\u003e\n  \u003cli\u003eIf experts themselves disagree on the right answer: ambiguity, flagged for human discussion.\u003c/li\u003e\n\u003c/ul\u003e\n\n\u003ch3\u003eCompilation: Surgical Multi-Agent Edits\u003c/h3\u003e\n\n\u003cp\u003eThe compiler translates each diagnosed issue into minimal file edits. Sub-agents analyze impact in parallel, examining cross-references, conflicts with existing positions, token budget impact, test coverage, and duplication risk.\u003c/p\u003e\n\n\u003cp\u003eTwo design choices make this trustworthy:\u003c/p\u003e\n\n\u003cul\u003e\n  \u003cli\u003e\u003cstrong\u003eIndependent adversarial review.\u003c/strong\u003e A separate agent, running in a fresh context with no knowledge of the improvement rationale, receives only the proposed diffs to the knowledge base. Its job is to find problems such as contradictions introduced, edge cases broken, or positions undermined. Because it shares no context with the proposing agents, it cannot inherit their blind spots.\u003c/li\u003e\n  \u003cli\u003e\u003cstrong\u003eDeterministic structural validation.\u003c/strong\u003e A linter catches issues programmatically: dangling cross-references, file size budget violations, identifier collisions, and dependency cycles. This layer is not probabilistic. It passes or fails.\u003c/li\u003e\n\u003c/ul\u003e\n\n\u003ch3\u003eEvaluation: Proving the Fix Works\u003c/h3\u003e\n\n\u003cp\u003eEvery proposed change goes through a two-stage validation:\u003c/p\u003e\n\n\u003cp\u003e\u003cstrong\u003eTargeted replay\u003c/strong\u003e runs the agent on the original scenario that triggered the feedback. The agent does not know it is being tested. A separate judge evaluates the new output against the original expert feedback without knowing what was changed. This deliberately blind design prevents confirmation bias. If targeted replay fails, compilation is retried.\u003c/p\u003e\n\n\u003cp\u003e\u003cstrong\u003eRegression testing\u003c/strong\u003e runs multiple benchmarks for that domain, which are usually structured test suites of Q\u0026amp;A pairs. For analytical domains where there might be multiple correct answers, an independent LLM judge gives each test case a pass/fail based on certain criteria. The agent is run in parallel, independent sessions against the benchmark questions, and regressions in performance are detected. If regression testing fails, compilation is retried with an updated prompt describing where the agent regressed, along with the original issue and attempted fix.\u003c/p\u003e\n\n\u003ch3\u003eLanding and Enrichment: Compounding Returns\u003c/h3\u003e\n\n\u003cp\u003eThe output of the pipeline is a pull request (diff) with a complete audit trail. A human expert reviews a proven fix rather than debugging a raw failure. Once approved and landed (the knowledge file or recipe is updated), the original failing scenario and its validated correct answer are automatically added to the regression test suite. This means every fix permanently raises the bar and future changes to the knowledge system must preserve the behavior that was just corrected.\u003c/p\u003e\n\n\u003ch2\u003eResults\u003c/h2\u003e\n\n\u003cp\u003eAfter three development sprints spanning six weeks, the system achieved:\u003c/p\u003e\n\n\u003cul\u003e\n  \u003cli\u003eDomain SMEs rated agent outputs \u003cstrong\u003euseful almost all the time\u003c/strong\u003e, a significant improvement from early versions where outputs frequently required substantial rework.\u003c/li\u003e\n  \u003cli\u003e\u003cstrong\u003eDays to minutes\u003c/strong\u003e reduction in individual assessment time.\u003c/li\u003e\n  \u003cli\u003e\u003cstrong\u003eAutomated self-improvement\u003c/strong\u003e producing validated knowledge edits at a rate that previously required full engineering sprints.\u003c/li\u003e\n  \u003cli\u003e\u003cstrong\u003eZero regressions\u003c/strong\u003e across improvement cycles, with every fix automatically strengthening the regression suite.\u003c/li\u003e\n  \u003cli\u003eDomain experts consistently reported the agent handles the \u003cstrong\u003evast majority of the analytical work\u003c/strong\u003e, allowing them to focus on the genuinely ambiguous cases that require human judgment.\u003c/li\u003e\n\u003c/ul\u003e\n\n\u003ch2\u003eApplying This Architecture\u003c/h2\u003e\n\n\u003cp\u003eThe specific domain we built this for required synthesizing dozens of sources (both internal positions and external material) into risk-weighted assessments. But the architecture is domain-independent. It applies wherever:\u003c/p\u003e\n\n\u003cul\u003e\n  \u003cli\u003eSpecialist knowledge lives as tribal knowledge in experts' heads.\u003c/li\u003e\n  \u003cli\u003eConsistency across assessments matters.\u003c/li\u003e\n  \u003cli\u003eThe volume of work exceeds available expert capacity.\u003c/li\u003e\n  \u003cli\u003eOff-the-shelf LLMs produce inadequate analysis.\u003c/li\u003e\n\u003c/ul\u003e\n\n\u003cp\u003eConcrete domains where this pattern fits include regulatory compliance, protocol adherence, financial risk assessment, security review, engineering standards compliance, and procurement evaluation. The common thread is that organizations need AI systems with genuine institutional expertise, not just general knowledge.\u003c/p\u003e\n\n\u003cp\u003eThe requirements for adopting this architecture are:\u003c/p\u003e\n\n\u003cul\u003e\n  \u003cli\u003eA \u003cstrong\u003estructured knowledge system\u003c/strong\u003e with explicit file boundaries, cross-references, and a dependency graph (the organizational second brain for the domain).\u003c/li\u003e\n  \u003cli\u003eA \u003cstrong\u003eprocedural layer\u003c/strong\u003e that separates domain knowledge from analytical methodology (recipes).\u003c/li\u003e\n  \u003cli\u003eAn \u003cstrong\u003eautomated evaluation suite\u003c/strong\u003e that grows with each improvement cycle.\u003c/li\u003e\n  \u003cli\u003e\u003cstrong\u003eHuman-in-the-loop checkpoints\u003c/strong\u003e calibrated to the domain's risk tolerance.\u003c/li\u003e\n\u003c/ul\u003e\n\n\u003cp\u003eThe deeper principle is straightforward: keep the complexity in text files that are readable by both humans and agents, rather than fine-tuned model weights. Every improvement is a text edit that a domain expert can review in 30 seconds. Every change is version-controlled, diffable, and reversible. The compilation pipeline is sophisticated, but its outputs are always transparent.\u003c/p\u003e\n\n\u003cp\u003eThe goal is a system where expert effort compounds permanently. Every expert interaction makes the system better. Every correction persists as a verified improvement. The organization's collective knowledge stops being trapped in individuals and starts being available, consistently and at scale, to everyone who needs it.\u003c/p\u003e\n\n\u003ch2\u003eAcknowledgements\u003c/h2\u003e\n\n\u003cp\u003eThe authors would like to express their gratitude to the contributions of the following people, who have played a crucial role in developing this system. class="blog-content"><div><h2>An Organizational Second Brain: Building an AI That Learns From Experts</h2>

<p><em>Source: <a href="https://engineering.fb.com/2026-09-02/ml-applications/organizational-second-brain-ai-learns-from-experts/" target="_blank" rel="noopener">Engineering at Meta</a>, by Shaurya Sengar, Jason Nawrocki, Jay Shah and Prashant Kommireddi, September 2, 2026</em></p>

<ul>
  <li>We have built an AI agent that acts as a secondary expert for a given domain, making deep specialist knowledge readily available and preserved for anyone in an organization to access, share, and build upon.</li>
  <li>This is not a typical domain-specific agent. Its novelty comes from integrating two layers:
    <ul>
      <li>A structured, auditable <strong>knowledge architecture</strong> separates what the agent knows from how it reasons.</li>
      <li>A <strong>self-improvement loop</strong> then compiles expert feedback into verified, regression-tested updates <strong>without model retraining</strong>.</li>
    </ul>
  </li>
  <li>Together, these two layers turn one-off expert corrections into permanent, compounding institutional memory, and the pattern is designed to generalize to other domains governed by retrievable text rather than model weights.</li>
  <li>This system is saving domain subject matter experts (SMEs) at Meta substantial time, allowing them to focus more on the work where their knowledge matters most.</li>
</ul>

<p>Many large organizations have the same problem when it comes to specialist knowledge. While some of it is written down in the form of models, playbooks, checklists, and frameworks, the most valuable specialist knowledge lives in people's heads and rarely gets captured anywhere durable. In compliance domains, for example, the same types of questions can arise across hundreds of product reviews, expert assessments take days of manual research, and inconsistency between assessments creates real organizational risk.</p>

<p>It is not uncommon for experts to spend more time answering routine questions than on genuinely novel and ambiguous work where their judgment matters most. We need systems that can capture how an organization's experts reason and make that knowledge available to everyone who needs it, so that expertise is easier to share, build on, and preserve.</p>

<p>We set about solving this challenge by codifying institutional intelligence into an AI agent for a specific compliance domain. The agent combines a knowledge system that acts as the organization's "second brain," a reasoning layer that mirrors how domain experts actually think, and an automated improvement pipeline that compounds expert effort permanently. The patterns generalize to any enterprise domain with deep specialist knowledge, whether that is finance, security, or engineering.</p>

<h2>The Architecture at a Glance</h2>

<p>Off-the-shelf LLMs provide a strong foundation, but they often need deeper institutional context to be fully effective in specialist domains. Without that grounding, a general purpose model has limited value given it will not be able to distinguish between what an organization <em>could</em> do (a summary of general information) and what it <em>should consider</em> doing (based on historic positions, company direction, business context, etc.). In high-stakes domains, closing this gap requires supplying the model with the organization's own knowledge and priorities so its analysis reflects how the organization actually reasons.</p>

<p>The system we have designed has four layers, each solving a distinct problem:</p>

<table>
  <thead>
    <tr><th>Layer</th><th>Problem It Solves</th><th>Key Insight</th></tr>
  </thead>
  <tbody>
    <tr>
      <td>Knowledge System</td>
      <td>Institutional knowledge is scattered and inaccessible to AI.</td>
      <td>LLMs are better at managing knowledge than people. Structure knowledge as a navigable filesystem, optimized for LLM consumption.</td>
    </tr>
    <tr>
      <td>Reasoning Pipeline</td>
      <td>Expert analysis follows structured methodologies that monolithic prompts cannot capture.</td>
      <td>Separate what the agent knows from how it reasons, using composable procedures we call recipes. This enables progressive disclosure, where the agent doesn't have to remember all the instructions at once.</td>
    </tr>
    <tr>
      <td>Evaluation Framework</td>
      <td>You cannot improve what you cannot measure.</td>
      <td>Develop automated benchmarks that grow with each improvement cycle to enable confident iteration.</td>
    </tr>
    <tr>
      <td>Self-Improvement Loop</td>
      <td>Manual feedback cycles take weeks and do not scale.</td>
      <td>Treat knowledge maintenance as a compilation problem with automated verification.</td>
    </tr>
  </tbody>
</table>

<p>These layers depend on each other. The knowledge system's file structure makes automated editing possible. The reasoning layer's explicit procedures make failure attribution tractable. The evaluation framework gates every change. And the improvement loop feeds back into both knowledge and reasoning. Remove any one layer and the others degrade.</p>

class="transition-transform duration-200 group-hover:translate-x-0.5" aria-hidden="true">→</span></span></a></div></div></aside><div><h2>Building the Organizational Second Brain</h2>

<p>Large organizations can accumulate thousands of documents as a byproduct of expert work. It is tempting to treat those documents as organizational knowledge, but the real knowledge is implicit: how experts reason, what they prioritize, and how they resolve ambiguity. An agent that retrieves document chunks at inference time has to re-derive that reasoning from raw sources on every run, which is slow, error-prone, and inconsistent.</p>

<p>We make that implicit knowledge explicit ahead of time. A long-running offline process reasons through source documents and distills them into structured knowledge files - curated statements of how the organization interprets its domain, with constraints, boundaries, and routing implications made machine-readable.</p>

<p>Most significantly, that knowledge then forms the basis of a feedback loop that allows the agent to learn from and implement feedback from human experts without the underlying model having to be retrained.</p>

<p>The industry has converged on a similar idea. Andrej Karpathy's <a href="https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f" target="_blank" rel="noopener">LLM Wiki</a> structures agent knowledge as a navigable graph of files, and Google's <a href="https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing" target="_blank" rel="noopener">Open Knowledge Format</a> standardizes this for cross-agent interoperability. The shared insight is that knowledge should be pre-extracted, explicitly structured, and progressively disclosed rather than re-derived on every query. We extended these principles into a system where citation fidelity and institutional consistency are non-negotiable, organizing 200+ files into a strict taxonomy:</p>

<ul>
  <li><strong>Position files</strong> capture authoritative organizational stances: how the organization has decided to interpret a given domain question, along with its constraints, boundary conditions, and machine-actionable routing implications that tell the reasoning layer when to apply it.</li>
  <li><strong>Taxonomy and vocabulary files</strong> act as an authoritative glossary for the terms the organization uses to describe its domain, such as entity types, activity categories, and classification tiers. Each is maintained as a single source of truth so the agent and the organization use language consistently.</li>
  <li><strong>Routing indexes</strong> map input characteristics to the relevant positions and procedures, determining which files apply without relying on embedding similarity alone. This makes retrieval deterministic and auditable.</li>
  <li><strong>Gateway files</strong> define threshold tests the agent must pass before entering an analytical domain, preventing it from applying specialized knowledge where it does not belong.</li>
</ul>

<p>Every file declares its dependencies (<code>depends_on</code>) and consumers (<code>referenced_by</code>) in YAML frontmatter, forming a bidirectional dependency graph. When one file changes, you can trace exactly what else might be affected, which matters when the self-improvement loop proposes automated edits.</p>

<figure>
  <img src="/static/img/blog/meta-organizational-second-brain/knowledge-system.body.webp" data-full-src="/static/img/blog/meta-organizational-second-brain/knowledge-system.png" alt="The knowledge system: files organized as a navigable filesystem, with YAML frontmatter declaring triggering scenarios, dependencies and consumers" width="1280" height="751" loading="eager" decoding="async" fetchpriority="high">
  <figcaption>An illustration of the knowledge system: files are organized as a navigable filesystem (left), and each file's YAML frontmatter (right) declares when it applies (the triggering scenarios) plus its dependencies and consumers, forming a bidirectional dependency graph the agent can traverse and maintain easily.</figcaption>
</figure>

<h2>Organizing Knowledge by Density and Usage Frequency</h2>

<p>A key architectural decision is how to partition knowledge between the curated wiki and supplementary retrieval (RAG). We split on <strong>information density and expected usage frequency</strong>.</p>

<p><strong>High-density, frequently referenced sources go into the wiki</strong>: distilled files capturing how the organization reasons, such as positions, decision frameworks, boundary examples, and strategic interpretations. The agent consults these on nearly every turn. Because they encode the organization's evolving thinking, they need to stay current, and the wiki structure makes them easy to update, version, and validate.</p>

<p><strong>Sparse, situationally relevant sources are served through semantic or lexical search (RAG)</strong>: documents that matter deeply when they apply but are not needed in detail on most runs, such as detailed reference material, individual product specifications, historical decision records, and niche external knowledge. Loading all of them into the wiki would bloat the system and dilute attention.</p>

<p>The result is that the agent's core reasoning is always grounded in the most refined, current organizational knowledge, while it can still reach for supporting evidence when a scenario demands it. The combination produces an organizational second brain that encodes <em>how</em> the organization interprets and applies information, rather than only where to find it.</p>

<h2>Expert Reasoning via Composable Recipes</h2>

<p>Knowledge alone is not enough. Domain experts do not simply recall facts, they follow structured methodologies: a financial analyst works through a valuation model step by step, a security engineer follows a threat modeling procedure. The challenge is capturing those methodologies in a form an LLM can execute reliably.</p>

<p>We solve this with <strong>composable procedures we call recipes</strong>. Where knowledge files are declarative, recipes are imperative. Each one prescribes a multi-step analytical workflow, specifying what to examine first, which knowledge to load at each step, what decision procedures to follow, and what constitutes a complete analysis.</p>

<p>The critical design choice is <strong>separating what the agent knows from how it reasons</strong>. Recipes reference knowledge files but contain no domain facts; knowledge files state positions but prescribe no procedures. This means:</p>

<ul>
  <li>Adding an organizational position means adding a knowledge file and updating a routing index. No recipe changes.</li>
  <li>Fixing a flaw in the agent's methodology means editing a recipe. No knowledge files change.</li>
  <li>Failures attribute cleanly to one layer. Was the knowledge wrong, or the procedure?</li>
</ul>

<p>Recipes compose into pipelines, much like a head chef's master recipe for a dinner service delegates to sub-recipes for each component (the sauce, the protein, the garnish) without containing those details itself. Our top-level routing recipe examines the input and selects which downstream recipes to invoke, each handling one analytical phase.</p>

<p>This is also what enables <strong>progressive disclosure</strong>. Rather than front-loading a monolithic instruction set covering every possible scenario, each recipe step carries only the instructions and knowledge relevant to that phase. Early versions used a single flat instruction file and loaded all sources via semantic search, pulling a large volume of mixed-relevance files into the context window on every run. After restructuring into recipe-driven stages, each query touches only a small, targeted subset, cutting tokens consumed per turn by around 80%. Context windows are finite and attention degrades with volume, so delivering the right instructions at the right time directly improves reasoning quality.</p>

<h2>Keeping Humans in Control</h2>

<p>Human experts stay in control of this system throughout. The agent accelerates and structures their work; it does not replace their judgment or their authority over the outcome.</p>

<p>We enforce this through two mechanisms:</p>

<ul>
  <li><strong>Checkpoints</strong> are defined points in the analysis where the agent surfaces its intermediate reasoning for expert review before proceeding, and the expert can confirm, correct, or redirect.</li>
  <li><strong>Escalations</strong> trigger when the agent hits genuine ambiguity, whether from underspecified inputs or evidence that supports more than one defensible reading. Rather than forcing a resolution, it hands the question to the expert, whose choice determines the path the analysis takes.</li>
</ul>

<p>Checkpoints and escalations serve three purposes simultaneously:</p>

<ul>
  <li><strong>Quality and direction control</strong>: experts catch errors before they compound downstream, and keep the analysis on the path they consider most relevant.</li>
  <li><strong>Training signal</strong>: every correction and every escalation becomes input for the self-improvement loop.</li>
  <li><strong>Trust calibration</strong>: experts build confidence incrementally by observing the agent's reasoning rather than just its final output, and by seeing it flag uncertainty instead of masking it.</li>
</ul>

<p>The more consequential the decision, the more this matters, which is why we recommend keeping a human in the loop by default across domains like compliance, financial risk assessment, security review, and engineering safety.</p>

<h2>The Self-Improvement Flywheel</h2>

<p>We consider the self-improvement flywheel to be the most distinctive part of this system. While the structured knowledge system and composable recipes produce a system that is legible by humans and agents, testable, and modular, the number of interdependent files makes manual maintenance impossible to scale. When domain experts provide feedback to an agent that feedback has to be translated into precise file edits. This process can take weeks because it requires understanding the full dependency graph, verifying nothing else breaks, and validating the fix actually works.</p>

<p>There has been a large body of work - from RAG memory systems to model-weight knowledge editing - devoted to addressing how agents store, retrieve, and update knowledge. But much less attention has gone toward <strong>keeping a document-based institutional knowledge base correct</strong> as it grows and as expert positions evolve. Agents that auto-draft their own fixes are increasingly common; but we have not seen this level of validation rigor applied to a structured knowledge base without model retraining.</p>

<p>We treat that maintenance as a <strong>compilation problem</strong> and automate it. Every expert correction moves through four phases:</p>

<ol>
  <li>Diagnose expert feedback into actionable issues with their root cause.</li>
  <li>Compile issues into minimal verified edits.</li>
  <li>Validate that fixes work without regressions.</li>
  <li>Have domain experts review them.</li>
</ol>

<p>Once the loop completes, the regression test suite is enriched with the issue that was just fixed so that future updates preserve this behavior.</p>

  <img src="/static/img/blog/meta-organizational-second-brain/self-improvement-loop.body.webp" data-full-src="/static/img/blog/meta-organizational-second-brain/self-improvement-loop.png" alt="The self-improvement loop: diagnose, compile, evaluate, review and land, then fold the fix back into the regression suite" width="1280" height="714" loading="lazy" decoding="async">
  <figcaption>The self-improvement loop. Expert corrections are diagnosed to their root cause, compiled into minimal verified edits, and evaluated against replay and regression tests before they are reviewed and landed. </figure>

<h3>Diagnosis: Attributing Each Correction to a Root Cause</h3>

<p>Raw expert feedback comes from conversation traces where domain SMEs interacted with the agent and provided corrections. The diagnosis phase extracts structured signals from these conversations.</p>

<p>Our first approach classified feedback by conversational form. If the expert provided information, it must be a knowledge gap; if they redirected the agent, it must be a procedure problem. This heuristic failed because conversational form is a poor proxy for root cause. An expert correcting a conclusion might be exposing a knowledge gap, a recipe flaw, or a genuine ambiguity.</p>

<p>The working approach separates extraction from classification. First, extract every substantive signal from the expert alongside the agent's full knowledge manifest (every file loaded, when, and how used). Second, read the actual knowledge files and apply a single attribution test: <em>could the agent have reached the correct conclusion from its source materials?</em></p>

<ul>
  <li>If the materials contained the right answer but the agent still erred: recipe problem.</li>
  <li>If the materials did not contain the right answer: knowledge gap.</li>
  <li>If experts themselves disagree on the right answer: ambiguity, flagged for human discussion.</li>
</ul>

<h3>Compilation: Surgical Multi-Agent Edits</h3>

<p>The compiler translates each diagnosed issue into minimal file edits. Sub-agents analyze impact in parallel, examining cross-references, conflicts with existing positions, token budget impact, test coverage, and duplication risk.</p>

<p>Two design choices make this trustworthy:</p>

<ul>
  <li><strong>Independent adversarial review.</strong> A separate agent, running in a fresh context with no knowledge of the improvement rationale, receives only the proposed diffs to the knowledge base. Its job is to find problems such as contradictions introduced, edge cases broken, or positions undermined. Because it shares no context with the proposing agents, it cannot inherit their blind spots.</li>
  <li><strong>Deterministic structural validation.</strong> A linter catches issues programmatically: dangling cross-references, file size budget violations, identifier collisions, and dependency cycles. This layer is not probabilistic. It passes or fails.</li>
</ul>

<h3>Evaluation: Proving the Fix Works</h3>

<p>Every proposed change goes through a two-stage validation:</p>

<p><strong>Targeted replay</strong> runs the agent on the original scenario that triggered the feedback. The agent does not know it is being tested. A separate judge evaluates the new output against the original expert feedback without knowing what was changed. This deliberately blind design prevents confirmation bias. If targeted replay fails, compilation is retried.</p>

<p><strong>Regression testing</strong> runs multiple benchmarks for that domain, which are usually structured test suites of Q&amp;A pairs. For analytical domains where there might be multiple correct answers, an independent LLM judge gives each test case a pass/fail based on certain criteria. The agent is run in parallel, independent sessions against the benchmark questions, and regressions in performance are detected. If regression testing fails, compilation is retried with an updated prompt describing where the agent regressed, along with the original issue and attempted fix.</p>

<h3>Landing and Enrichment: Compounding Returns</h3>

<p>The output of the pipeline is a pull request (diff) with a complete audit trail. A human expert reviews a proven fix rather than debugging a raw failure. Once approved and landed (the knowledge file or recipe is updated), the original failing scenario and its validated correct answer are automatically added to the regression test suite. This means every fix permanently raises the bar and future changes to the knowledge system must preserve the behavior that was just corrected.</p>

<h2>Results</h2>

<p>After three development sprints spanning six weeks, the system achieved:</p>

<ul>
  <li>Domain SMEs rated agent outputs <strong>useful almost all the time</strong>, a significant improvement from early versions where outputs frequently required substantial rework.</li>
  <li><strong>Days to minutes</strong> reduction in individual assessment time.</li>
  <li><strong>Automated self-improvement</strong> producing validated knowledge edits at a rate that previously required full engineering sprints.</li>
  <li><strong>Zero regressions</strong> across improvement cycles, with every fix automatically strengthening the regression suite.</li>
  <li>Domain experts consistently reported the agent handles the <strong>vast majority of the analytical work</strong>, allowing them to focus on the genuinely ambiguous cases that require human judgment.</li>
</ul>

<h2>Applying This Architecture</h2>

<p>The specific domain we built this for required synthesizing dozens of sources (both internal positions and external material) into risk-weighted assessments. But the architecture is domain-independent. It applies wherever:</p>

<ul>
  <li>Specialist knowledge lives as tribal knowledge in experts' heads.</li>
  <li>Consistency across assessments matters.</li>
  <li>The volume of work exceeds available expert capacity.</li>
  <li>Off-the-shelf LLMs produce inadequate analysis.</li>
</ul>

<p>Concrete domains where this pattern fits include regulatory compliance, protocol adherence, financial risk assessment, security review, engineering standards compliance, and procurement evaluation. The common thread is that organizations need AI systems with genuine institutional expertise, not just general knowledge.</p>

<p>The requirements for adopting this architecture are:</p>

<ul>
  <li>A <strong>structured knowledge system</strong> with explicit file boundaries, cross-references, and a dependency graph (the organizational second brain for the domain).</li>
  <li>A <strong>procedural layer</strong> that separates domain knowledge from analytical methodology (recipes).</li>
  <li>An <strong>automated evaluation suite</strong> that grows with each improvement cycle.</li>
  <li><strong>Human-in-the-loop checkpoints</strong> calibrated to the domain's risk tolerance.</li>
</ul>

<p>The deeper principle is straightforward: keep the complexity in text files that are readable by both humans and agents, rather than fine-tuned model weights. Every improvement is a text edit that a domain expert can review in 30 seconds. Every change is version-controlled, diffable, and reversible. The compilation pipeline is sophisticated, but its outputs are always transparent.</p>

<p>The goal is a system where expert effort compounds permanently. Every expert interaction makes the system better. Every correction persists as a verified improvement. The organization's collective knowledge stops being trapped in individuals and starts being available, consistently and at scale, to everyone who needs it.</p>
