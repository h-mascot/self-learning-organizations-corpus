capability.</p><p>Bigger models. Longer context windows. More tools. More autonomy.</p><p>We now have agents that can write code, investigate systems, interact with APIs, and complete multi-step workflows that would have seemed impossible just a few years ago.</p><p>But if you’ve built and deployed these systems, you’ve probably encountered the same problem.</p><p><strong>The agent works... until it doesn’t.</strong></p><p>A small change gets deployed. A workflow starts behaving differently. A user says the results feel worse.</p><p>Then the questions begin:</p><ul><li><p>What changed?</p></li><li><p>Did we improve one capability while breaking another?</p></li><li><p>Is this a real regression or just randomness?</p></li><li><p>How do we know whether the system is actually getting better?</p></li></ul><p>At that point, the problem is no longer model capability.</p><p>The problem is reliability.</p><p>This is where agent development is heading next.</p><p>We’re moving from building agents to building verifiable agent systems. Systems that don’t just perform work, but can prove they performed it correctly.</p><p>That shift is being driven by one important idea:</p><p><strong>Eval-driven development is what turns agents from interesting demos into production systems.</strong></p><div><hr/></div><h2 class="header-anchor-post">The First Wave of Agent Architecture<div class="pencraft pc-display-flex pc-alignItems-center pc-position-absolute pc-reset header-anchor-parent"><div class="pencraft pc-display-contents pc-reset pubTheme-yiXxQA"><div class="pencraft pc-reset header-anchor offset-top" id="§the-first-wave-of-agent-architecture"></div><button class="pencraft pc-reset pencraft iconButton-mq_Et5 iconButtonBase-dJGHgN buttonBase-GK1x3M buttonStyle-r7yGCK size_sm-G3LciD priority_secondary-S63h9o" tabindex="0" type="button" data-href="https://davepatten.substack.com/i/200047822/the-first-wave-of-agent-architecture"><svg xmlns="http://www.w3.org/2000/svg" width="18" height="18" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide lucide-link"><path d="M10 13a5 5 0 0 0 7.54.54l3-3a5 5 0 0 0-7.07-7.07l-1.72 1.71"></path><path d="M14 11a5 5 0 0 0-7.54-.54l-3 3a5 5 0 0 0 7.07 7.07l1.71-1.71"></path></svg></button></div></div></h2><p>Most modern agents follow a familiar pattern.</p><p>They combine four core elements:</p><ul><li><p>Skills</p></li><li><p>Context</p></li><li><p>Memory</p></li><li><p>Execution</p></li></ul><p><strong>Skills</strong><span> allow agents to interact with APIs, run code, query systems, and take actions.</span></p><p><strong>Context</strong><span> keeps those actions relevant. It provides the information, constraints, and environment needed to make good decisions.</span></p><p><strong>Memory</strong><span> allows agents to retain information across interactions. It captures prior decisions and prevents the system from starting from scratch every time.</span></p><p><strong>Execution</strong><span> systems coordinate everything. They manage workflows, retries, checkpoints, and long-running tasks.</span></p><p>Together, these capabilities enabled a wave of innovation.</p><p>We built coding agents, research assistants, customer support systems, and operational automation workflows.</p><p>But there was still a missing piece.</p><p>None of these components answer a simple question:</p><p><strong>How do you know the agent is actually working correctly?</strong></p><div><hr/></div><h2 class="header-anchor-post">When “It Feels Worse” Becomes a Real Problem<div class="pencraft pc-display-flex pc-alignItems-center pc-position-absolute pc-reset header-anchor-parent"><div class="pencraft pc-display-contents pc-reset pubTheme-yiXxQA"><div class="pencraft pc-reset header-anchor offset-top" id="§when-it-feels-worse-becomes-a-real-problem"></div><button class="pencraft pc-reset pencraft iconButton-mq_Et5 iconButtonBase-dJGHgN buttonBase-GK1x3M buttonStyle-r7yGCK size_sm-G3LciD priority_secondary-S63h9o" tabindex="0" type="button" data-href="https://davepatten.substack.com/i/200047822/when-it-feels-worse-becomes-a-real-problem"><svg xmlns="http://www.w3.org/2000/svg" width="18" height="18" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide lucide-link"><path d="M10 13a5 5 0 0 0 7.54.54l3-3a5 5 0 0 0-7.07-7.07l-1.72 1.71"></path><path d="M14 11a5 5 0 0 0-7.54-.54l-3 3a5 5 0 0 0 7.07 7.07l1.71-1.71"></path></svg></button></div></div></h2><p>In the early stages of development, teams often rely on manual testing.</p><p>The system is small. The changes are obvious. Feedback arrives quickly.</p><p>As complexity grows, that approach stops working. A change gets deployed.</p><p>Something feels different. Users notice. Nobody knows exactly why. </p><ul><li><p>Was performance actually worse?</p></li><li><p>Which component caused the issue?</p></li><li><p>Did fixing one problem create another?</p></li></ul><p>Without structured evaluation, teams are forced to guess.</p><p>This creates a familiar cycle:</p><ul><li><p>Build. Ship. React.</p></li><li><p>Fix one issue.</p></li><li><p>Accidentally create another.</p></li><li><p>Discover it after users do.</p></li></ul><p>This is the point where experimentation becomes engineering.</p><div><hr/></div><h2 class="header-anchor-post">Evals Are the Missing Layer<div class="pencraft pc-display-flex pc-alignItems-center pc-position-absolute pc-reset header-anchor-parent"><div class="pencraft pc-display-contents pc-reset pubTheme-yiXxQA"><div class="pencraft pc-reset header-anchor offset-top" id="§evals-are-the-missing-layer"></div><button class="pencraft pc-reset pencraft iconButton-mq_Et5 iconButtonBase-dJGHgN buttonBase-GK1x3M buttonStyle-r7yGCK size_sm-G3LciD priority_secondary-S63h9o" tabindex="0" type="button" data-href="https://davepatten.substack.com/i/200047822/evals-are-the-missing-layer"><svg xmlns="http://www.w3.org/2000/svg" width="18" height="18" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide lucide-link"><path d="M10 13a5 5 0 0 0 7.54.54l3-3a5 5 0 0 0-7.07-7.07l-1.72 1.71"></path><path d="M14 11a5 5 0 0 0-7.54-.54l-3 3a5 5 0 0 0 7.07 7.07l1.71-1.71"></path></svg></button></div></div></h2><p>At its simplest, an evaluation measures whether a system successfully completes a task.</p><p>For agents, however, evaluation goes far beyond checking a single response.</p><p>Agents perform actions.</p><ul><li><p>They call tools.</p></li><li><p>They modify state.</p></li><li><p>They make decisions across multiple steps.</p></li></ul><p>A coding agent may claim it fixed a bug while the tests still fail. A support agent may report that a refund was processed even though no transaction exists. A research agent may generate a convincing answer that contains factual errors.</p><p>The lesson is simple:</p><p><strong>Outcomes matter more than outputs.</strong></p><p>Evals force us to measure what actually happened, not just what the model said happened.</p><div><hr/></div><h2 class="header-anchor-post">Automated Sanity Checks at Scale<div class="pencraft pc-display-flex pc-alignItems-center pc-position-absolute pc-reset header-anchor-parent"><div class="pencraft pc-display-contents pc-reset pubTheme-yiXxQA"><div class="pencraft pc-reset header-anchor offset-top" id="§automated-sanity-checks-at-scale"></div><button class="pencraft pc-reset pencraft iconButton-mq_Et5 iconButtonBase-dJGHgN buttonBase-GK1x3M buttonStyle-r7yGCK size_sm-G3LciD priority_secondary-S63h9o" tabindex="0" type="button" data-href="https://davepatten.substack.com/i/200047822/automated-sanity-checks-at-scale"><svg xmlns="http://www.w3.org/2000/svg" width="18" height="18" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide lucide-link"><path d="M10 13a5 5 0 0 0 7.54.54l3-3a5 5 0 0 0-7.07-7.07l-1.72 1.71"></path><path d="M14 11a5 5 0 0 0-7.54-.54l-3 3a5 5 0 0 0 7.07 7.07l1.71-1.71"></path></svg></button></div></div></h2><p>One way to think about agents is this:</p><ul><li><p>Agents perform the work.</p></li><li><p>Humans sanity check the results.</p></li></ul><p>That works for a handful of tasks. It does not work for thousands. Humans cannot reliably review every output, every edge case, or every workflow variation.</p><p>Evals solve that problem.</p><p>They become automated sanity checks at scale. They allow teams to define what success looks like, test realistic scenarios, and identify regressions before users encounter them. </p><p>That distinction separates experimental systems from success looks like.</p><p>That makes iteration faster and more objective.</p><p>You no longer guess whether changes helped.</p><p>You measure.</p><p>And contrary to popular belief, you don’t need thousands of test cases to begin.</p><p>A small collection of realistic scenarios, especially those based on real failures, can provide meaningful signal surprisingly quickly.</p><div><hr/></div><h2 toward it.</p><p>Measure continuously.</p><p>The difference is that agent systems are probabilistic and adaptive.</p><p>Exact outputs matter less.</p><p>Successful outcomes matter Longer context windows. More tools. More autonomy.</p><p>We now have agents that can write code, investigate systems, interact with APIs, and complete multi-step workflows that would have seemed impossible just a few years ago.</p><p>But if you\u2019ve built and deployed these systems, you\u2019ve probably encountered the same problem.</p><p><strong>The agent works... until it doesn\u2019t.</strong></p><p>A small change gets deployed. A workflow starts behaving differently. A user says the results feel worse.</p><p>Then the questions begin:</p><ul><li><p>What changed?</p></li><li><p>Did we improve one capability while breaking another?</p></li><li><p>Is this a real regression or just randomness?</p></li><li><p>How do we know whether the system is actually getting better?</p></li></ul><p>At that point, the problem is no longer model capability.</p><p>The problem is reliability.</p><p>This is where agent development is heading next.</p><p>We\u2019re moving from building agents to building verifiable agent systems. Systems that don\u2019t just perform work, but can prove they performed it correctly.</p><p>That shift is being driven by one important idea:</p><p><strong>Eval-driven development is what turns agents from interesting demos into production systems.</strong></p><div><hr></div><h2>The First Wave of Agent Architecture</h2><p>Most modern agents follow a familiar pattern.</p><p>They combine four core elements:</p><ul><li><p>Skills</p></li><li><p>Context</p></li><li><p>Memory</p></li><li><p>Execution</p></li></ul><p><strong>Skills</strong> allow agents to interact with APIs, run code, query systems, and take actions.</p><p><strong>Context</strong> keeps those actions relevant. It provides the information, constraints, and environment needed to make good decisions.</p><p><strong>Memory</strong> allows agents to retain information across interactions. It captures prior decisions and prevents the system from starting from scratch every time.</p><p><strong>Execution</strong> systems coordinate everything. They manage workflows, retries, checkpoints, and long-running tasks.</p><p>Together, these capabilities enabled a wave of innovation.</p><p>We built coding agents, research assistants, customer support systems, and operational automation workflows.</p><p>But there was still a missing piece.</p><p>None of these components answer a simple question:</p><p><strong>How do you know the agent is actually working correctly?</strong></p><div><hr></div><h2>When \u201CIt Feels Worse\u201D Becomes a Real Problem</h2><p>In the early stages of development, teams often rely on manual testing.</p><p>The system is small. The changes are obvious. Feedback arrives quickly.</p><p>As complexity grows, that approach stops working. A change gets deployed.</p><p>Something feels different. Users notice. Nobody knows exactly why. </p><ul><li><p>Was performance actually worse?</p></li><li><p>Which component caused the issue?</p></li><li><p>Did fixing one problem create another?</p></li></ul><p>Without structured evaluation, teams are forced to guess.</p><p>This creates a familiar cycle:</p><ul><li><p>Build. Ship. React.</p></li><li><p>Fix one issue.</p></li><li><p>Accidentally create another.</p></li><li><p>Discover it after users do.</p></li></ul><p>This is the point where experimentation becomes engineering.</p><div><hr></div><h2>Evals Are the Missing Layer</h2><p>At its simplest, an evaluation measures whether a system successfully completes a task.</p><p>For agents, however, evaluation goes far beyond checking a single response.</p><p>Agents perform actions.</p><ul><li><p>They call tools.</p></li><li><p>They modify state.</p></li><li><p>They make decisions across multiple steps.</p></li></ul><p>A coding agent may claim it fixed a bug while the tests still fail. A support agent may report that a refund was processed even though no transaction exists. A research agent may generate a convincing answer that contains factual errors.</p><p>The lesson is simple:</p><p><strong>Outcomes matter more than outputs.</strong></p><p>Evals force us to measure what actually happened, not just what the model said happened.</p><div><hr></div><h2>Automated Sanity Checks at Scale</h2><p>One way to think about agents is this:</p><ul><li><p>Agents perform the work.</p></li><li><p>Humans sanity check the results.</p></li></ul><p>That works for a handful of tasks. It does not work for thousands. Humans cannot reliably review every output, every edge case, or every workflow variation.</p><p>Evals solve that problem.</p><p>They become automated sanity checks at scale. They allow teams to define what success looks like, test realistic scenarios, and identify regressions before users encounter them. </p><p>That distinction separates experimental systems from production-grade platforms.</p><div><hr></div><h2>The Agent Harness and the Eval Harness</h2><p>One of the most important concepts in modern agent engineering is the separation between runtime execution and evaluation.</p><p>The <strong>agent harness</strong> runs the system.</p><p>It orchestrates tools, manages memory, coordinates workflows, and produces outputs.</p><p>The <strong>eval application runtime and a CI/CD testing pipeline.</p><p>You would never deploy production software without testing.</p><p>Agent systems should be treated the same way. </p><p>The same applies here. <a href=\\\"https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents\\\">Anthropic makes this distinction explicit</a>: the agent harness enables the system to act, while the evaluation harness is what measures whether it is actually working.</p><div><hr></div><h2>Designing Effective Evals</h2><p>Not all evaluations provide useful signal.</p><p>Strong evaluation systems typically combine three approaches.</p><h3>Deterministic Checks</h3><p>These verify objective outcomes.</p><p>Examples include:</p><ul><li><p>Unit test results</p></li><li><p>State validation</p></li><li><p>API responses</p></li><li><p>Security controls</p></li></ul><p>They are fast and reliable, but sometimes too rigid.</p><h3>Model-Based Evaluations</h3><p>LLMs evaluate quality, reasoning, completeness, or relevance.</p><p>These provide flexibility but require calibration and monitoring.</p><h3>Human Evaluation</h3><p>Humans remain the best judges of nuanced or subjective outcomes.</p><p>However, human review is expensive and difficult to scale.</p><p>The strongest evaluation systems combine all three.</p><div><hr></div><h2>Capability vs Regression</h2><p>There are two feedback loops every team should track.</p><h3>Capability Evals</h3><p>These measure what the agent can do today.</p><p>Success rates start low and improve over time.</p><h3>Regression Evals</h3><p>These protect existing functionality.</p><p>Once an agent learns a behavior, regression tests ensure it doesn\u2019t lose that capability later.</p><p>Over time, today\u2019s capability tests become tomorrow\u2019s regression suite.</p><p>This creates a continuous cycle of growth and reliability.</p><div><hr></div><h2>A Coding Agent Example</h2><p>Imagine a coding agent tasked with fixing a security vulnerability.</p><p>A weak evaluation checks whether code was generated.</p><p>A strong evaluation asks:</p><ul><li><p>Did the tests pass?</p></li><li><p>Did the fix introduce regressions?</p></li><li><p>Did the agent follow secure coding practices?</p></li><li><p>Did it interact with the codebase correctly?</p></li><li><p>Did static analysis detect new issues?</p></li></ul><p>The difference is significant.</p><p>You are no longer evaluating a response.</p><p>You are evaluating a system operating within a real environment.</p><div><hr></div><h2>Building with Evals First</h2><p>Adopting eval-driven development changes how teams work.</p><p>Instead of:</p><p><strong>Build \u2192 Test \u2192 Ship \u2192 React</strong></p><p>You move toward:</p><p><strong>Define Success \u2192 Build \u2192 Measure \u2192 Improve</strong></p><p>This forces clarity from the start.</p><p>Before building the agent, you define what success looks like.</p><p>That makes iteration faster and more objective.</p><p>You no longer guess whether changes helped.</p><p>You measure.</p><p>And contrary to popular belief, you don\u2019t need thousands of test cases to begin.</p><p>A small collection of realistic scenarios, especially those based on real failures, can provide meaningful signal surprisingly quickly.</p><div><hr></div><h2>The Evolution of Testing</h2><p>If you\u2019ve used Test-Driven Development (TDD) or Behavior-Driven Development (BDD), this should feel familiar.</p><p>TDD asks:</p><blockquote><p>Did the function return the correct value?</p></blockquote><p>BDD asks:</p><blockquote><p>Did the system behave as expected?</p></blockquote><p>Eval-driven development asks:</p><blockquote><p>Did the agent successfully complete the task in the real environment?</p></blockquote><p>The principle remains the same.</p><p>Define correctness first.</p><p>Build toward it.</p><p>Measure continuously.</p><p>The difference is that agent systems are probabilistic and adaptive.</p><p>Exact outputs matter less.</p><p>Successful outcomes matter more.</p><div><hr></div><h2>The Most Underrated Practice</h2><p>One of the best ways to improve an agent system is surprisingly simple.</p><p>Read the transcripts.</p><p>Execution traces reveal:</p><ul><li><p>How the agent reasoned</p></li><li><p>Which tools it selected</p></li><li><p>Where failures occurred</p></li><li><p>How recovery happened</p></li><li><p>Whether the issue came from the model, environment, or evaluation process</p></li></ul><p>Metrics tell you what happened.</p><p>Transcripts often tell you why.</p><p>That intuition becomes invaluable over time.</p><div><hr></div><h2>The Bigger Shift</h2><p>We\u2019re beginning to move beyond individual agents.</p><p>What is emerging looks more like an operating system for intelligent systems.</p><p>These platforms combine:</p><ul><li><p>Execution harnesses</p></li><li><p>Memory layers</p></li><li><p>Tool ecosystems</p></li><li><p>Evaluation pipelines</p></li><li><p>Monitoring systems</p></li><li><p>Continuous feedback loops</p></li></ul><p>At that scale, the most important question is no longer:</p><p><em>\u201CHow smart is the model?\u201D</em></p><p>The more important question becomes:</p><p><em>\u201CHow reliably can the system be measured, improved, and trusted?\u201D</em></p><div><hr></div><h2>From Capability to Verifiability</h2><p>The first wave of AI agents focused on capability. That work delivered incredible progress. The next wave will focus on trust.</p><ul><li><p>Skills make agents useful.</p></li><li><p>Context makes them relevant.</p></li><li><p>Memory makes them persistent.</p></li><li><p>Execution makes them scalable.</p></li><li><p><strong>Evals make them trustworthy.</strong></p></li></ul><p>If there\u2019s one lesson from teams building production agent systems today, it\u2019s this:</p><p><strong>You cannot scale agents without evaluation.</strong></p><p>Start early. Define success clearly. Test real scenarios. Combine multiple evaluation approaches. Most importantly, understand how your system behaves, not just what it outputs. Because the future isn\u2019t about building agents that can act.</p><p>It\u2019s about building systems that can do the work and prove they did it correctly.</p><p>That\u2019s what transforms agents into infrastructure.</p><div><hr></div><p>Want the full deep dive? <strong>Check out my full article on Medium</strong>.</p><p>\uD83D\uDE80 Stay tuned for more posts in <strong>AI Security &amp; Development</strong>!
