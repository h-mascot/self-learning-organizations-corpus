<p class="wp-block-paragraph" data-styleid="style-su3rjhejk">Many AI platforms now offer memory as a feature, meant to give the agents context about how you work, what you&#8217;ve been doing recently, how you write, and the data and services you&#8217;re connected to.</p>



<p class="wp-block-paragraph" data-styleid="style-1ng6ezgdi">Most of them focus on the person: your details, your preferences, your history. What they tend to overlook is the work: the tasks people run, the requirements attached to them, the deliverables those tasks produce, and the conventions a team settles into along the way.</p>



<p class="wp-block-paragraph" data-styleid="style-1ng6ezgdi">We approached memory with the context of enterprise knowledge work as our main focus. When an agent reviews an account or prepares a customer response, the relevant context is the organizational knowledge that shapes how that task should be done.</p>



<p class="wp-block-paragraph" data-styleid="style-1ng6ezgdi">We announced the customer-facing details of our memory feature <a href="https://writer.com/blog/enterprise-brain/">here</a>. This post is about how we built it, what we chose to optimize for, and why we believe this approach, which is quite different to personal or project based memory, is needed to produce strong results for enterprise organizations.</p>



<h2 id="h-what-we-built-and-what-it-s-for" class="wp-block-heading" data-styleid="style-r4tjcy7cl">What we built, and what it&#8217;s for</h2>



<p class="wp-block-paragraph" data-styleid="style-z2j51ofsq">Our research indicates that many memory systems are designed with recall of personal facts in mind. A common approach is to treat information from conversations as different abstract types: people,  places, events, etc. These systems are well-suited to remembering that you have a dog named Biscuit, that Cindy is your boss, and that you send Cindy an email update each Wednesday at 4pm, because you leave early that day to take Biscuit to her dog trainer.<br><br>While personal memory is mapped as a connected graph of named entities, enterprise knowledge is often retrieved by running retrieval augmented generation on connected data &#8211; both stored locally and from connected apps and services. The system would take a user query and search for relevant documents, spreadsheets, and slide decks that each retrieval or extraction pass must re-process through RAG.</p>



<p class="wp-block-paragraph" data-styleid="style-i0464y4nc">Enterprise work requires a different set of abstractions to capture the higher order structure of how and why your organization does work in a certain way. This structure must be able to represent things like how your organization qualifies a sales opportunity or triages a last minute compliance check. We deliberately still store personal facts, but only as a part of this broader set of enterprise knowledge.</p>



<p class="wp-block-paragraph" data-styleid="style-on2huljky">Agent Memory is built on an opinionated ontology that is tailored to the shape of enterprise work. When ingesting content, we pull out tasks and their requirements, the deliverables they produce, the projects they roll up into, and the conventions a person establishes while doing the work. While it is true that other memory systems can be adapted to different domains through custom ontologies, Agent Memory arrives out of the box with a structure we found through our experimentation to work well for enterprise use.</p>



<p class="wp-block-paragraph" data-styleid="style-yszvf88x4">Because we favor organizational context over the personal, Agent Memory also explicitly supports records that are shared between users in a team. In an enterprise, one hard problem is capturing diffuse, institutional knowledge: a convention someone established should reach a colleague who was never in that conversation. That is most of what onboarding is, and it does not scale by writing documentation many employees may just skim or skip entirely. Having this content available via Agent Memory means that it can be injected into the user’s sessions exactly when they need it.</p>



<h2 id="h-ingestion-four-decisions-not-one" class="wp-block-heading" data-styleid="style-l1wpzvx3t">Ingestion: four decisions, not one</h2>



<p class="wp-block-paragraph" data-styleid="style-00ulqjct4">One concern of any memory system is how to deal with new information in light of what is already known. A new conversation turn that is sent to the system could contain important facts about a sales opportunity, or an update that the opportunity has been converted. We require a strategy to ensure that our retrieval system only returns true information to the agent.</p>



<p class="wp-block-paragraph" data-styleid="style-9k26t7z2w">We first compare each extracted record with what is already stored.&nbsp; We either add it, update an existing record, delete one that no longer holds, or match, that is, recognize the fact is already there and write nothing. The goal of using this operation set is that the memory store should contain neither duplicate nor stale information.</p>



<p class="wp-block-paragraph" data-styleid="style-s9268lrjb">Appending a dozen phrasings of the same convention over months means that retrieval will return redundant information that potentially blocks out our ability to return other, useful data under our token budget. In the case where we have stale data, retrieval has to arbitrate at query time, under a latency budget. Maintaining a clean data store is the most efficient form of solving these problems.</p>



<p class="wp-block-paragraph" data-styleid="style-tjeck7s5a">In our system, updates don&#8217;t overwrite. We retain a superseded version of the record and link it to its replacement, so the history of a belief stays inspectable. We make these changes so anyone can find a detailed answer about what was removed and why.</p>



<h2 id="h-ontology-aware-retrieval" class="wp-block-heading" data-styleid="style-njpubdkhs">Ontology-aware retrieval</h2>



<p class="wp-block-paragraph" data-styleid="style-gb1q9zmmm">The goal of our retrieval system is to return a compact set of useful information. It operates in two stages: building a candidate set and re-ranking. Our candidate set is built from parallel lexical and semantic searches. Both are required for the enterprise scenario. Account names, dates, and project codes are most reliably returned by lexical search, while semantic search means the system can identify information about a delayed launch, even if the transcript of the meeting about this decision never uses the actual name of the launch.</p>



<p class="wp-block-paragraph" data-styleid="style-gb1q9zmmm">We expand our candidate set by making use of enterprise-specific ontology. Recalled records pull in their immediate neighbors if they are relevant, so a hit on any part of a work item returns the whole item rather than a fragment. For example, if a requirement appears in our candidate set, its connected task will also be added. The goal of this process is to increase the recall of the candidate set over truly useful items.</p>



<p class="wp-block-paragraph" data-styleid="style-gb1q9zmmm">We then apply a re-ranker to the candidate set and return those above a score threshold. This means that we return a variable number of only highly relevant memories.</p>



<h2 id="h-scoping-what-three-people-learn-the-team-inherits" class="wp-block-heading" data-styleid="style-6malmojeh">Scoping: What three people learn, the team inherits</h2>



<p class="wp-block-paragraph" data-styleid="style-nb97zxol9">Agent Memory includes a system to promote some user-level records to the team level. It is critical that this system only promotes appropriate material, both to preserve user privacy and to ensure usefulness.</p>



<p class="wp-block-paragraph" data-styleid="style-qfytvmti0">Two rules are used to decide what is promoted. First, a team record is created only when three different people have independent user-level records stating the same information. Second, the information has to generalize: it has to be useful to the team, not only the users who derived it.</p>



<p class="wp-block-paragraph" data-styleid="style-qfytvmti0">We developed the system to exclude individual working preferences, personal schedules, and personal details. These rules are strict, and could mean that useful records are not shared with the team because the conditions are not met. We accept this to help ensure that anything personal or sensitive stays where it is.</p>



<p class="wp-block-paragraph" data-styleid="style-qfytvmti0">What gets written at the team level is a summary, not a copy. The system composes a fresh statement of the shared convention from the records that support it rather than lifting anyone&#8217;s text, so team memory reads as something the team knows rather than an excerpt from a colleague&#8217;s session.</p>



<p class="wp-block-paragraph" data-styleid="style-sfkc1qnhb">We paid special attention to handling disagreements between different users. We wanted memories that were supported by enough users to be shared with the team, even if the support was not unanimous. In cases where some users disagreed with the position, we made sure that the team record described both the majority position and the dissenting one. The record is kept live while at least three users continue to be in the majority. Every team-level record keeps provenance back to the records it was created from for audit reasons.</p>



<h2 id="h-the-benchmark-we-re-building" class="wp-block-heading" data-styleid="style-f5l2xe39i">The benchmark we&#8217;re building</h2>



<p class="wp-block-paragraph" data-styleid="style-6fn8hk3n1">We started this article by discussing our focus on building a memory system that works for enterprises. In this domain, a memory system must retain the <em>task</em> someone was running, the requirements attached to it, what it produced, or the precedent a decision set for the next piece of work. These form a structure that accumulates across conversations.</p>



<p class="wp-block-paragraph" data-styleid="style-ihlauvq0n">Memory evaluation benchmarks are beginning to be created to measure this application of a memory system. They test things like the ability to share conversational knowledge and governance around sharing facts, but do so separately. We have not found a benchmark that provides a complete evaluation of governed organisational memory: how practices, requirements and work products are established, scoped, revised and applied across a company.</p>



<p class="wp-block-paragraph" data-styleid="style-6t3dy84va">We have built a benchmark that is drawn from professional sessions: conversations where people plan campaigns, review accounts, make decisions, and settle how recurring work gets handled. Each of these is paired with a later task that depends on what came before.</p>



<p class="wp-block-paragraph" data-styleid="style-58akx3krf">We have built this benchmark to reflect the capabilities that a memory system must have when serving enterprise users. Institutional knowledge and conventions form when people enact them while working, rather than someone always stating that “our policy is X”. In our dataset, the information needed to complete a task is expressed in this way. The tasks are also made harder by sharing minimal vocabulary with the initial sessions: enterprises expect the same ways of working to be applied no matter the client or occasion.</p>



<p class="wp-block-paragraph" data-styleid="style-t9hooi0qo">We adopt a graded approach to evaluation. Rather than one verdict per scenario, we break each expected effect of memory into a separate checkable property of the output. If an earlier review established that an opportunity qualifies only with confirmed budget, an identified decision-maker, and a timeline inside six months, then a later account review missing the budget can be judged on three counts independently. Open-ended work has many valid shapes; this lets us check each way the earlier context should have shown up without insisting on one right answer.</p>

<p class="wp-block-paragraph" data-styleid="style-g8x2ya0yn">We are eager to share additional results from our memory evaluations soon. In addition, we plan to publish pieces that go deeper on the ontology and the abstractions that decide what gets written, updated, or dropped as memories form. And for the engineers who like to hear about the most interesting (and painful) parts, we’ll walk through why we started on a graph database and ultimately moved to Postgres for enterprise-scale memory.</p>

        function setCookie(name, value, days = 2) {
            const expirationDate = new Date();
            expirationDate.setDate(expirationDate.getDate() + days);
            document.cookie = `${name}_${value}=true; expires=${expirationDate.toUTCString()}; path=/`;
        }

        function getCookie(name) {
            const value = `; ${document.cookie}`;

            if (parts.length === 2) {

            return null;
